# ADR-0002：项目列表「倒序 + 状态筛选」下沉到 API（`after_id` 键集方向翻转 + 新增 `product_id` 过滤）

- **状态**：**已确认**（决策来源：需求卡 `t_01M83XY4XGEYT1G8F8NMN5GG9N` 返工驳回指令「排序和筛选都需要改后端的接口」，2026-11-23）
- **决策人**：需求评审方（返工指令）；记录与方案落地：CTO
- **日期**：2026-11-23
- **上游**：issue #133（enhancement，OPEN）；PRD `prd-issue-133-projects-sort-filter-v0.1.md`（原非目标 1 被本 ADR 推翻）
- **证据基准**：`Casper-Mars/echuan@6484e3fa85579f1f023dcc9bc7cd46a01a4ad7e3`（`main`，已 `git fetch --prune`）+ 只读 `GET /v1/projects?limit=100`（`http://echuan:8720`，2026-11-23，13 条）
- **影响面**：`internal/store/v3/project.go`、`internal/api/v3_handlers.go`（+ 测试）、`api/openapi.yaml`、`kit/`（`listV3Projects` 透传与 `echuan_project_list` 工具描述）、`web/src/api/client.ts` 与项目列表屏、2 份 tech 文档、1 份屏规格
- **可逆性判定**：**数据可逆、对外语义不可逆**。无 schema 变更、无数据迁移，代码层 `git revert` 即回退；但 `next_after_id` 的方向语义与列表顺序一旦被外部 agent 消费，回退等于再次翻转语义，需要二次通知。因此本条按「有 ADR 的契约变更」处理，而不是实现层细节。

---

## 1 决策问题

**「新建项目排最前」和「按状态筛选」这两件事，是在浏览器里对一页数据重排/过滤，还是由 `GET /v1/projects` 承担？**

- 直接触发：issue #133 的两条诉求（顺序、筛选）。
- 约束来源：需求评审方明确要求**两条都改后端接口**（v0.1 方案取「前端呈现层」被驳回）。
- 真正需要拍板的是第二层：一旦把顺序下沉到 API，`after_id`/`next_after_id` 这对键集游标的**方向**要不要跟着翻转；以及要不要同时补 `product_id` 过滤 —— 这两件事决定了这次改动是「加个参数」还是「翻一个契约」。

## 2 决策

1. **排序下沉**：`GET /v1/projects` 统一 `ORDER BY p.id DESC`（新建在前）。`after_id` 的键集方向翻转为 `p.id < ?`；`next_after_id` 改为返回**本页最后一条（即本页最小）id**，语义变为「取更早一页的游标」。行为形态（末页仍返回最后一条 id、客户端再请求得到空页）保持现状，不新增 `has_more`。
2. **筛选下沉到服务端**：`GET /v1/projects?status=open|closed`（既有能力，前端改为真正传参）+ **新增可选 `product_id` 过滤**（业务 id，过滤条件落在既有 JOIN 的 `pr.product_id` 上 —— `projects.product_id` 是指向 `products(id)` 的内部外键，`migrations/0001_init.sql:49`）。
3. **前端不排序、不做状态过滤**：列表顺序与集合完全由服务端决定；前端只保留一层防御性 `product_id` 再过滤（见 §4 C3）。
4. **不新增接口、不新增 `total`/`has_more` 字段、不改默认 `limit=50`、不做 UI 分页**（PRD §9-2 仍延后）。
5. **`product_id` 的异常口径**：空串视同未传；不存在的 `product_id` 返回空 `items`（不 404）—— 它是过滤参数，不是资源定位。

## 3 关键权衡（为什么连 `product_id` 一起补）

必须承认：**只翻排序方向、不补 `product_id`，会让今天最糟的失败模式变得更糟。**

| 方案 | 单页 50 条内 | 全局项目超 50 条时 | 结论 |
|---|---|---|---|
| 现状（ASC，无产品过滤） | 老项目在前 | 新产品落在第 51 条之后 → **新建的项目看不见**（issue 的原始痛点） | 不做 |
| 只翻 DESC，仍无产品过滤 | 满足 issue | 页内是「全局最新 50 条」再按产品挑 → **老产品可能整表为空**，且「看 newest」变成「看 newest 恰好是这台产品的」 | 单独做会把痛点从「看不到最新」换成「什么都看不到」，否决 |
| **DESC + `product_id` 过滤（本 ADR）** | 满足 issue | 页内是「该产品最新 50 条」→ 只缺最旧，主诉求（新建排最前）始终成立 | **选它** |

代价：`product_id` 参数与倒序一起发布，等于一次动两个契约点；但拆开发布会让中间态（DESC 无产品过滤）产生新的「空列表」故障，比一次性改更危险。

其余被否决的做法：

- **新开一个倒序端点**（如 `GET /v1/projects?order=desc` 或 `/v1/projects/recent`）：多一条长期维护的契约分支，且 `after_id` 语义在同一路由内出现两种方向，消费方更容易踩错。否决。
- **加 `order` 参数保持两种顺序兼容**：本期没有「要升序」的需求方（`kit`/agent 有 `after_id` 用法，但没有「必须从旧到新」的业务依赖，仓库内检索无消费方依赖升序语义）；先加开关等于把不存在的需求固化进契约。若未来出现，按 §6 退出条件加参数。
- **只改前端呈现（v0.1 方案）**：被评审方明确驳回（要求改后端接口）。本 ADR 不重开该选项。

## 4 约束

- **C1**：不新增路由、不改响应字段集合（`items[]` + `next_after_id` 形态不变，只改语义与顺序）；`api/openapi.yaml` 的 operation 集合不变，因此 `internal/contract` 的路由测试不需要新增条目。
- **C2**：默认 `limit` 仍为 50（`internal/store/v3/project.go:87-89`）；本期不做 UI 分页，但语义翻转后 `next_after_id` 可直接支撑「加载更早」。
- **C3**：前端在拿到响应后仍按 `product_id` 再过滤一次（1 行），用于兜住「新前端 + 未升级后端」的部署窗口 —— 该窗口下旧后端会忽略 `product_id`，若前端不兜会**串产品显示**。这是部署防线，不是筛选机制。
- **C4**：`status` 非法值仍 400 `invalid_argument`（`v3_handlers.go:235-243`），前端只会传 `open`/`closed`/不传。
- **C5**：不加索引。依据：`ix_projects_product (product_id, seq_no)`（`migrations/0001_init.sql:61`）已可按产品收窄，产品下项目量级 ≤ 50；新增 `(product_id, id)` 属未验证的优化，不做（§7 U1）。

## 5 后果

**正面**：顺序与筛选只有一个真相（服务端），UI 不再维护第二套排序/过滤逻辑；`next_after_id` 成为可用的「更早一页」游标，为 PRD §9-2 的分页铺路；`product_id` 过滤让「产品维度」在服务端成立，顺带降低「全局项目增长后看不到自己产品」的风险。

**负面**：

1. **对外语义翻转**：任何依赖「`after_id` 升序翻页」的外部消费方会被静默改变。仓库内消费方是 `kit`（`kit/src/client.ts:1339` 透传、`kit/src/tools/v3.ts:469-491` 工具 schema），随本次同步更新并改写工具描述；仓库外消费方无清单可得（U3），只能靠发布说明。
2. **单产品超 50 条仍缺最旧**（既有局限延后，PRD §9-2）。
3. **每次筛选切换一次网络往返**（换来的是「不串状态」的单一口径）：需要区分「首屏 loading」与「切换重拉」两个子态，否则筛选控件会在重拉时消失，用户回不到「全部状态」。
4. **回滚不是免费的**：代码 `revert` 容易，但已发布给 agent 的语义要再翻转一次；回滚须同时回滚前端（否则旧前端 + 新后端出现「顺序已倒但前端还在本地过滤」的混合态 —— 该混合态功能可用，但顺序与旧版一致地「已倒」，见 §6 回滚表）。

## 6 回滚与退出条件

**回滚（发布后 24h 内）**：`git revert <实现提交>`（store/handler/openapi/kit/web/文档同一提交）→ `make test` → `make web` → `make build` → 重发。数据无需回滚（无 schema/数据变化）。回滚后顺序恢复为「老项目在前」，`after_id` 恢复升序语义，需在同一条发布说明里说明二次变化。

**什么证据会推翻本决策**：

1. 出现「必须按旧→新取页」的消费方（外部 agent 或新屏），且无法用一次查询内排序解决 → 加 `order=asc|desc` 参数或另开只读端点，本 ADR 修订为「双序」方案；
2. 产品下项目数常态化超过单页上限 → PRD §9-2 立项，届时同时改 `limit`/分页与 UI 加载更多，本 ADR 的「不做分页」条款作废；
3. 若评审方改为要求「只改后端排序、不改筛选」（或反之），本 ADR 范围按指令收窄，另一条留在前端并单独登记。
