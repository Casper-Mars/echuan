# ADR-0001：Web UI 重做采用 Mantine 8 组件库 + 自建 ui/ 封装层

- **状态**：**已确认**（决策人 2026-11-19 答复三项范围问题；技术选型未被推翻）
- **决策人**：Casper（产品与技术负责人）
- **提出**：CTO（架构决策岗）
- **日期**：2026-11-19
- **上游**：[issue #76 重构web ui](https://github.com/Casper-Mars/echuan/issues/76)
- **证据基准**：`main@3cdc89e`（与线上 `/version` 返回的 commit 一致）
- **影响面**：`web/`、构建产物 `internal/web/dist/`；不改 `/v1` 契约、不改数据库

---

## 1. 决策问题

**「Web UI 重做」的技术底座选哪一套——继续手写 CSS、引入组件库、还是只引无样式原语——并据此确定移动端能力与样式锁定的边界。**

可逆性判定：**部分不可逆**。样式层与组件调用面一旦铺满 6 个页面，再换库等于重做样式层；业务逻辑（`api/`、hooks、路由）不受影响，所以不是全栈不可逆。本 ADR 的职责是把「样式层更换」的成本从"重写页面"压到"重写封装层"，见 §6 护栏。

## 3. 现状（问题陈述的证据）

- `web/src` 共 3794 行，其中 `styles.css` **2613 行，占 69%**。
- 单个样式文件里并存**两个 `:root` 令牌块**（17 个 + 5 个变量，两套词汇：`--border/--muted` 与 `--line/--ink-2`）。
- **39 个选择器被定义 2–3 次**（`.shell`、`.sidebar`、`.sidebar-link`、`.content`、`.product-grid`、`.modal-xlarge` 等）。
- 两套并存的看板实现：`.board-column*`（旧）与 `.board-col*`（新）。
- 308 个类名中，**269 个可静态判定**，其中 **148 个（55%）在 TSX 中从未被引用**；含整块死子系统 `.board-column*`、`.row-*`、`.notice-*`、`.spinner`。
- 侧栏在 `≤1024px` 收成 56px 图标栏、**导航文字全部隐藏**，4 个入口无标签。

结论：**代码不是烂的**（类型完整、hook 干净），烂的是样式层——三代视觉系统叠在一个文件里互相覆盖。所以本次重做的重心是样式层与信息架构，不是重写业务代码。

## 4. 选项与代价

六维：成本 / 工期（相对量级，不写人日）/ 复杂度 / 锁定 / 运维 / 组织。

### A. 不做（维持手写 CSS，只修具体缺陷）

- 成本：0 新增风险；工期：最小。
- 代价：148 个死类与三套叠加继续增长；C2 移动端无预算改善；C4「减轻开发压力」不满足；C5「都很难用」不解决。
- 结论：**作为基线保留，不作为方案**——它只回答"值不值得做"，而 C5 已经回答了"必须做"。

### B. Tailwind 4 + Radix 原语（shadcn 模式，组件复制进仓库）

- 成本：中高（看板、表格、上传、日期选择器、抽屉都要自建组合层）。
- 体积：`radix-ui@1.8.1` 全包 74 KB gz（按需更小），`tailwindcss@4.3.5` 构建层 0 运行时依赖。锁定：**最低**（Tailwind 是可移除的构建层，Radix 只提供无障碍原语）。
- 视觉自由：**最高**，C3 完全满足。
- 移动端：靠 Tailwind 断点自建，C2 能达成但工作量大。
- 与 C4 冲突：**不减轻开发压力，反而增加**——这是把它从主选降为退出路径的唯一原因。

### C. Mantine 8（`@mantine/core` + `hooks` + `notifications` + `dates` + `modals`）

- 版本事实：`@mantine/core@8.3.18` peer 为 `react ^18.x || ^19.x` → **与现有 React 18.3.1 兼容，无需升级 React**。
- 体积：全包 427 KB / **128 KB gz**，依赖 6 个（bundlephobia 实测；树摇后应低于此值，未实测）。
- 组件面：AppShell（响应式布局壳）、Drawer/Modal、Tabs、Table、表单控件、日期、通知、Spotlight——覆盖 C1/C2/C4 所需。
- 视觉自由：主题经 CSS 变量覆盖，C3 可达成（需原型验证）。
- 锁定：**中**。样式体系为 CSS Modules + CSS 变量（v7 起无运行时 CSS-in-JS），可在 `ui/` 封装层内替换。
- 移动端：AppShell 断点 + Drawer 可配置为底部抽屉；**手势拖动不在核心库**，若需带动画的底部面板要补 `vaul`（1 个额外依赖，见假设 A2）。
- 运维：纯 npm 依赖，无服务端组件，构建链不变。

### D. Ant Design 6（+ `antd-mobile` 补移动端）

- 版本事实：`antd@6.7.1` peer `react >=18` → 兼容。
- 成本：**最低**（企业后台组件最全：Table/Form/Upload/DatePicker/Drawer/Descriptions；Agent 训练语料最多，C6 下真实有优势）。
- 体积：全包 1.45 MB / **461 KB gz**，依赖 48 个 → 约为现状产物的 5.7 倍（gzip 对比 88 KB）。
- **与 C2 正面冲突**：移动端是 `antd-mobile@5.43` 另一套独立包，API 与视觉都不通用 → 同一功能要写两遍，或接受移动端体验割裂。这恰好放大 C6 的维护成本。
- 与 C3 冲突：视觉指纹强，要"认不出来"需覆盖大量 token + CSS-in-JS 覆盖；而现有 2613 行手写 CSS 与 CSS-in-JS 的优先级治理是额外负担。
- 锁定：**中高**。

### E. MUI（Material UI）——排除

Material 视觉识别度极强，与 C3 冲突；中文后台审美接受度低。列出以说明已评估，不展开。

## 5. 结论

**选 C：Mantine 8.x + 保留 React 18.3.1 + 自建 `web/src/ui/` 封装层。**

理由逐条对应约束：

1. **C4（减轻开发压力）**：C 提供成套组件，D 更彻底，B 不满足 → 先淘汰 B 作主选。
2. **C2（移动端）**：D 需两套库（antd + antd-mobile）才能达到同等体验，C 一套覆盖 → **这是淘汰 D 的决定性理由**。
3. **C3（允许认不出来）**：C 的令牌覆盖能力优于 D 的 CSS-in-JS 覆盖路径，且不引入两套样式体系打架的风险。
4. **C7（单二进制 + 体积）**：C 全包 128 KB gz，D 461 KB gz；移动网络上这是 3.6 倍差距。
5. **C8（React 18）**：C 8.x 明确支持 18.x，**不需要为 UI 重做连带升级 React**。

**明确不做**（边界，后续如需变更重新走决策）：

- 不升级 React 19。`@mantine/core@9.8.1` 要求 `react ^19.2.0`，但升级 React 对本次目标零收益、只增风险。**锁 Mantine 8.x 是刻意选择**，不是疏忽。
- **不同时使用 Tailwind 与 Mantine**：两套样式体系并存会重演今天"三代视觉叠加"的债务。
- 不替换 `react-router-dom@6`，不改 `marked` + `DOMPurify` 的 Markdown 渲染路径（已可用）。
- 不改 `/v1` 契约、不动数据库。**附件预览本期只做 markdown 正文**（前端 `fetch` 同源 `GET /v1/materials?id=` 直接渲染），**图片预览本期不做**（决策人 2026-11-19），因此后端零改动。

## 6. 关键护栏（把"部分不可逆"变"可替换"）

**业务页面禁止直接 `import '@mantine/core'`。所有组件经 `web/src/ui/` 封装层暴露。**

- 页面只能看见 `ui/` 的自有组件与语义化 props；Mantine 的 API 漏不到页面层。
- 更换 UI 库的成本 = 重写 `ui/`，而不是重写 6 个页面与信息架构。
- 这条护栏是本次选型的**生效前提**：护栏一旦破了，C 的锁定等级从中升到高，本 ADR 结论随之失效。
- 静态样式只保留一处入口（令牌层 + `ui/` 内的样式），并删除 148 个死类。重做完成后 `styles.css` 中"未引用类名"数量应显著低于 55%——这是可核查的验收指标，不是口号。

## 7. 退出条件与回滚

**退出条件（满足任一即推翻结论，转 B）**：

- E1：原型阶段实测树摇后包体积增量 **> 250 KB gz**（现状 88 KB gz，容忍上限约 3.8 倍）。
- E2：6 个页面中有 **≥3 个**必须大量 hack 主题才能达到目标视觉 → Mantine 主题表达力不足。
- E3：维护者在投入后反馈"改样式变成和库打架" 而非"省事"。
- E4：移动端必须自建手势/触控层，导致代码量反超自建方案。
- E5：Mantine 8.x 停止维护且 9.x 强依赖 React 19 → 要么连带升级 React（重开 ADR），要么转 B。

**回滚方式**：新 UI 在 feature 分支开发，`main` 不动；后端与 `/v1` 零改动，切换是纯前端产物替换。

- 回滚操作：revert 合并提交 → `make web` → `make build`，产物重新嵌入二进制。
- 回滚成本：低（无数据迁移、无契约变更、无外部集成）。
- 回滚前提：在合并前，`main` 的旧 UI 始终可构建可发布。
