# 项目需求与多技术方案

一个项目对应一条需求。需求文档保持一条版本链；技术方案可以有多份，每份具有稳定编号（如 `APP-1-S0001`）和独立版本链。标题和正文一起修订，历史内容只追加、不覆盖。本轮不包含 Word/PDF 上传、附件系统、删除方案或逐文档审批。

## 保存与评审

`project_specs.material_id` 持有独立方案当前版本；`materials.previous_material_id` 向前连接该文档历史。方案列表、全文及历史由 `GET /v1/specs` 读取；创建用 `POST /v1/specs`，修订用 `PATCH /v1/specs?id=方案编号`。修订必须带该独立文档版本的 `If-Match`，历史版本只能读取、下载。

只在项目处于规格评审（1）或规划中（2）时允许新建、修订方案。批准仍以项目为单位，针对全部当前方案；没有每份文档单独批准的状态。任意方案保存都会递增项目版本，使已打开页面的旧项目评审版本失效；进入任务清单评审及后续阶段后，不开放方案修改。保持原有需求编辑状态限制和项目状态迁移。

## 完整方案包与旧接口

`projects.spec_material_id` 保留为项目方案包当前版本指针。只有一份方案时，直接复用其资料和原历史链；多份时，按方案序号组合全部当前正文，在每段标明独立方案编号、标题、文档版本，写入新的方案包资料版本。方案包有自己的历史链与版本，不等于任何一份独立文档版本。

旧 `GET /v1/projects?id=` 的 `spec`、旧 `GET /v1/projects/materials?kind=2`、Worker 领取上下文的 `spec_version/spec_digest` 都继续表示完整方案包。既有客户端通过项目资料指针和下载接口获取完整内容，不会只取得最后保存的一份方案。**项目详情已不再返回 `requirement_md` 与 `spec_excerpt`**，正文一律走 `GET /v1/materials?id=`；网页对独立文档另有全文阅读入口。

旧 `POST /v1/projects/specs?id=项目编号` 修订第 1 份独立方案，而不是用一个文档替换全部集合。返回的 `spec` 和 `previous_material_id` 仍指向本次生成的项目方案包及其前一版；仅单文档时延续原有响应和链行为。旧调用未传标题时沿用项目标题这一既有行为。

所有任务使用所属项目的完整当前方案包，未加入按任务绑定特定方案的机制。领取接口、Worker 心跳与 kit 无需更改字段；查看独立文档可用新接口。

## 详情与正文分离

`GET /v1/projects?id=` 只返回索引与元数据：`requirement` / `spec` 两个资料引用（含 `material_id`），不返回 `requirement_md`、`spec_excerpt`。正文的唯一通道是 `GET /v1/materials?id=资料编号`（按内容寻址、带 `Cache-Control: immutable`）。写需求的请求体仍用 `requirement_md` / `body_md`，写通道不受影响。

这样详情响应与需求长度无关（38 万字需求下恒定在 1 KB 量级），前端 5 秒轮询不再重复搬运正文，服务端也不再为详情请求读磁盘。`detail()` 因此少了两次文件 IO 与一个失败面：资料文件缺失时详情仍能正常返回。

## 迁移与一致性

迁移 `0004` 将旧单方案及整条旧链作为第 1 份独立方案回填，保留资料编号、文件和版本。新表具备内部 `id`、稳定 `spec_id`、项目归属、序号、当前资料指针、创建及更新时间。

独立文档、项目方案包和项目版本在同一写事务保存。每份文档和最终方案包均受 `material_max_bytes` 限制（默认 20 MiB）；全部正文加标题、分隔符后超过限制则整笔拒绝，独立文档也不保存。失败仅清理本次新建对象，不删除既有共享对象。项目取消不会删除这些资料；具有方案的项目沿用原有不可直接删除约束。

## 网页操作

项目详情不再内联正文，只给需求版本链与资料元信息（含 `material_id`），正文按需下载或阅读；新增技术方案列表。“新建技术方案”创建一份独立文档；“阅读全文”打开完整正文与版本选择；当前版可编辑，历史版只读并可下载。“项目方案包摘要/历史”用于查看项目整体方案快照。
