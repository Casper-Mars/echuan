# 资产飞轮试点说明

本文说明资产飞轮试点要解决的问题、资产怎么分层、本仓当前的 pin，以及日常使用规则。

## 背景

现状是每张卡都在重新发明取证、环境与验证：同一套「起服务 → 等就绪 → 截图比对」在不同任务里被重写若干遍，判断标准还各不相同。
L5 的步数上限只是把这些重复劳动提前截断，治标不治本——步数降下来了，同样的活下一张卡还得再做一遍。
资产飞轮换个思路：把这些重复劳动抽出来沉淀成分层资产，写过一次就入库，下一张卡直接查、直接跑，把卡的篇幅留给真正的新增逻辑。

## 资产分层

四层自下而上逐级具体，越往下越通用、越往上越贴近本仓：

- **L0 原语**：跨领域的最小动作，如轮询服务就绪、对比截图差异、创建 git worktree，不含任何业务知识。
- **L1 runner**：一类任务的通用执行器，如读场景 JSON、驱动浏览器断言并截图的 `web-ui` runner，由数据驱动。
- **L2 场景包**：本仓的具体场景，如某页面的视口与断言、某接口的健康检查，跟代码走、随代码评审。
- **L3 staging**：卡内临时脚手架，第一次出现的重复动作先在这里落地，验证有效后再结算成上面三层或丢弃。

## 本仓 pin

本仓在 `.agent/assets.yaml` 里 pin 了 `library: "0.1.0"`，并声明 `runners.web-ui: "0.1.0"`。
共享库以只读方式挂载在容器内 `/opt/agent-assets/0.1.0`，索引为该目录下的 `registry.yaml`，`asset` 工具只认这份索引。
换版本是「改 pin + 换挂载」的独立动作，不在业务卡里顺手做。

## 使用方式

开工先用 `asset` 的 `search` 按 tags 查，命中且状态健康就直接 `run`，不再重写同类脚本；确实没有命中才动手写。
同一个动作在本项目第二次出现时，用 `create` 抽成 L3 脚手架并写清输入、输出与预期复用次数；跑通后按 `settle` 结算，
`promote-l2` 沉成项目场景包、`propose-l1` 提请升为共享 runner、`discard` 与 `debt` 分别记录作废与欠账。
`audit` 用于事后核对存量资产是否仍可用（健康度、入口有没有漂移）。两条硬规则：先查后写；每张卡结束必须 settle，不留无名脚本。

## 边界

共享库是数据不是包：它不是依赖、不注册工具、不含指令，只提供可读可跑的原语与 runner。
agent 不能直接改共享库；跨项目提升只能经 `settle` 的 `propose-l1` 生成 bundle、由人审 PR 落地。
L2 场景包跟代码走、进仓库一起演进；L3 只活在当卡，不长期驻留仓库。
